## 1. 修复：图片标记改写从「按名字通配」收紧为显式白名单

上游换成 `DeepSeek-V4.1-Flash` 之后，`internal/server/imgtag.go` 里
「模型名含 `deepseek` 就把 data URI 图片改写成 `<image_base64>` 标记」的通配规则失效了 ——
新模型不认这个标记，图被当成纯文本送进模型，而**全链路不报错**。

| | prompt_tokens | 结果 |
|---|---|---|
| 修复前 | 109,418 | 图被当纯文本内联，模型答「无法解码或识别画面内容」 |
| 修复后 | 361 | 正常视觉编码，画面描述与真图逐项吻合 |

改成配置项 `image_tag_models`（子串匹配，**默认空 = 一律透传标准 `image_url`**），
旧行为仍可按模型开启。

> 附带一个易复现的指纹：传 http(s) 图片 URL 时正常（改写只处理 `data:` 前缀），
> 传 data URI 就坏 —— 这正是「模型明明支持视觉却看不见图」的典型表现。

## 2. 修复：三条协议的图片都不再被静默降级成文本

两条转换桥都在丢图，且不报错：

- `internal/bridge/responses.go` 的 `ContentToText` 把 `input_image` 压成字面量 `"[image]"`
- `internal/bridge/anthropic.go` 的逐块循环**没有 `image` 分支**，Anthropic 的图块整块丢弃
  （纯图消息连整条 message 都不会发出）

新增 `internal/bridge/chatcontent.go` 统一拼 content：

- **无图仍返回纯字符串（旧行为逐字不变）**，有图才返回 content 数组
- 图片统一转成 `{"type":"image_url","image_url":{"url":…}}`，data URI 与 http(s) URL 都透传
- `tool_result` 里的图（截图类工具）也一并保住
- `ChatToResponse` 兼容数组形态正文（有的 OpenAI 兼容实现这么返回，否则会回一条空消息）
- 删掉已无人调用、却留着 `"[image]"` 地雷的 `ContentToText`

新增 8 条回归测试，覆盖两种 content 形态、base64/url 两种 source、纯图消息不丢、
以及 `/v1/messages` 与 `/v1/responses` 两条端到端接线。

## 3. 面板：11 个长列表统一分页

账号池 136 个账号时页面长到没法用，而所有列表都没有分页。

- 共用分页组件：每页 10/20/50/100/200（记在 `localStorage`），事件委托换页，
  筛选条件变化自动回第 1 页，数据变少自动回退页码
- 分页条挂在**横向滚动容器之外**：账号表实测 1236px 而容器只有 927px，
  放 `<tfoot>` 会跟着表格被滚出右边界
- 覆盖：账号池 / 积分到期 / 模型锁池 / 已下架模型 / 模型目录 / 按小时用量 /
  用量维度 / 积分扣除维度 / 请求记录 / 错误汇总 / 积分流水

同时修掉两个真问题：

- `loadLogs` 原本是 `Promise.all` + **空 catch**：一条慢请求会把「请求记录 / 错误汇总 /
  积分流水」三张表一起清空，控制台还没有任何线索
  → 改逐块渲染（谁回来先画谁）+ 单请求超时 + 可见报错；
  实测请求记录 300ms 出表，不再陪积分流水等 5 秒
- `/panel/api/credit_history` 串行遍历全池账号逐个打上游（136 账号实测 **57.9 秒**）
  → 并发 8 + 单账号 8s 超时 + 60s 缓存：**冷启 5.0s / 命中 0.03s**

## 4. 面板：账号池与请求记录加表头排序；「积分到期提醒」并入账号池

到期表的 133 行全部来自 `/overview` 的 accounts，与账号池是**同一批数据**；
而每日赠送按自然日滚动，几乎所有账号的到期日都是「明天」，独立成表信息密度极低，
却让页面多出一整屏。

- 账号池新增「到期」列（每日余额 + 剩余天数，今天到期标黄）并支持排序
- 表头加状态筛选：全部 / 可用 / 冷却中 / 已暂停选号 / 已禁用 / 有到期积分
- 顶部保留一行汇总（多少个账号有每日余额 · 合计 · 1 天内到期数）
- 表头排序只给**账号池（8 列）**与**请求记录（5 列）**加 —— 用量与模型目录本来就有
  排序下拉，错误汇总由后端按严重度聚合，积分流水/按小时天然是时间序，再加是噪音
- 数值列首次点击按降序（最大的先看）；到期与状态按升序；同列再点翻转方向

## 5. 面板：积分构成页 15s → 毫秒级

`/panel/api/packages` 对每个账号打 **3 个上游接口**（Quota + Points + FirstLogin），
并发只有 3，实测 **15.0s / 次**；前端又一次性渲染 **136 张卡片 + 135 个
「每账号一个 box + 一张表」**。

| 指标 | 优化前 | 优化后 |
|---|---|---|
| 接口（冷启 / 缓存命中） | 15.0s | **8.5s / 0.047s** |
| 页面首屏 | 16.0s | **1.7s**（缓存命中） |
| 页面元素 | 8,620 | **2,046**（该视图 7,184 → 610） |
| 页面高度 | 40,599px（28 屏） | **3,262px（2 屏）** |

改法：

- 并发 3 → 8
- **120 秒结果缓存**，`?force=1` 绕过（面板「刷新」按钮走这条）
- 凭证落盘移出并发段（原来每个账号都在并发额度里做一次文件写）
- 卡片与明细都分页；明细的 135 个 box 合并成**一张扁平表** + 分页

## 6. 面板：错误描述改成「当前状态」，下次成功后自动消失

账号池「状态」列下面那行灰字来自 `Account.lastError`，而它此前只在**「解冻」按钮**
里被清空过。于是两周前一次 401 留下的红字会一直挂着 —— 哪怕这个号之后跑了几千次
成功请求。错误描述因此变成了永久贴纸，真正需要看的失败反而被淹没在满屏旧错误里。

改法是把 `lastError` 明确定义为**当前状态**而不是历史：任何一次「该账号已恢复正常」
的操作都清掉它。

| 触发点 | 覆盖场景 |
|---|---|
| `Pool.ReportSuccess` → `NoteSuccess` | 走网关的成功请求（`/v1/*` 全部分支） |
| `ResetCooldowns` | 密码登录成功、短信登录成功、手动解冻、余额恢复后的自动解冻 |
| `doCheckinCtx` 成功分支 | 手动 / 全量 / 定时签到成功 |

失败历史不受影响：`Failures` 计数、账号池的 `成功/失败` 列、请求台账与日志都照旧，
排查仍然有据可查（`last_error` 本身不落盘，进程重启即清空，所以它只适合做「当前状态」）。

验证（另起一个临时实例 + 假上游，跑的是线上同一个镜像，**线上数据未参与**）：

| 步骤 | 面板上的错误描述 |
|---|---|
| 假上游回 401，加号触发自动签到 | `签到失败: /points/first-login HTTP 401` |
| 假上游恢复，手动签到一次（HTTP 200） | 空 |

新增用例：`TestLastErrorClearedOnSuccess`（pool 层）、
`TestCheckinSuccessClearsLastError`（panel 层，走真实 HTTP handler）。

## 7. 登录态判据：本地「到期」不作数，401 先复核再判死

上游登录响应**不返回过期时间**，本地 `expireAt` 是按客户端申请值（`"expire": 1209600`，
14 天）编出来的估计值。可上游那份凭证往往活得比它久 —— loomy2api 项目记过一次实锤
（账号 `loomy-3147` 本地已过期 6 小时，上游照常可用），并在 2026-10-16 为此定了模型：
**路由不看本地 TTL，凭证死活唯一权威是上游 401/403**。

本仓此前沿用「本地到期即摘号」，后果在实测数据上很清楚（166 个账号，2026-11-13）：

| 本地 expireAt 到期日 | 账号数 |
|---|---|
| 11-19 | 4 |
| 11-20 | 87 |
| 11-21 | 45 |
| 11-26 | 30 |

也就是 **11-21 池子从 166 掉到 30、11-26 归零**，而且不是慢慢死，是四天四刀。连带
（`SessionValid()` 被四处引用）：到期号不再选号、不再刷额度（余额恢复自动解冻也失效）、
刷额度里那次幂等 first-login 也停了（每日赠送额度不再入账），面板只打一行「请重新登录」——
而这些号**没有密码、手机号来自接码渠道**，这条建议给出的补救动作可能根本不存在。

改法三件套：

1. **本地 TTL 降级为展示**：`SessionValid()` → `HasSession()`（手里有凭证即可用），
   路由 / 额度刷新 / 签到 / `anySession()` 全部改判据；`expire_at` 只留在展示与日志里。
2. **401 先存疑、复核后才判死**：上游 401 → 账号立刻出池（不再拿客户端请求去踩），
   由 `probeSuspectSessions` 每 30 秒用最便宜的一次读接口（`/points/records`）复核：
   - 复核也 401/403 → `DropSession` 清空凭证 + 落盘 + 记下**实测寿命**（`observedLifetime`，
     唯一能学到真实 TTL 的时刻，也是补号节奏的依据）；
   - 复核通过 → 回池，当一次抖动；窗口到期也会自动回池，所以复核机制本身故障不会把号
     永久关在外面；连续 401 达 `session_drop_hits`（默认 3）直接判死作为兜底。
3. **面板一律报役龄**：`已服役 6.0 天`（事实）取代 `登录态 8.2d`（估计值），超过申请值
   标黄但**不代表不可用**；状态列新增「登录态复核中」；配置表单暴露复核窗口与判死阈值。

为什么不照搬 loomy2api 的「按役龄自动重登」：它只在**有密码**的账号上生效，而这套部署
166 个号**一个密码都没有**（凭证里只有 `loginid + session`，手机号是接码租的，补密码要
过短信验证）—— 搬过来是死代码。真正会在 11-21 发生的，是本地假 TTL 把还活着的号摘掉。

验证（隔离实例 + 假上游，跑的是线上同一个镜像，**线上数据未参与**）：

| 场景 | 结果 |
|---|---|
| 假上游回 401（客户端请求） | 账号出池、状态列显示「登录态复核中」，凭证还在 |
| 复核接口也回 401 | 清空登录态 + 记实测寿命 + 落盘；状态列转「登录态失效」 |
| 复核接口回 200 | 撤销存疑回池（日志 `登录态复核通过`） |

新增用例：`TestLocalExpiryDoesNotBlockRotation`（回归 loomy-3147）、
`TestFaultSessionSuspectThenDrop`、`TestFaultSessionDropAfterHits`、
`TestSuspectClearedBySuccess`、`TestObservedLifetimeRecordedOnce`、
`TestProbeSuspectSessionDropsDeadCredential`、`TestProbeSuspectSessionKeepsLiveCredential`、
`TestProbeSuspectSessionNetworkFailureNoVerdict`。

## 8. 每日赠送额度优先：把「今天会作废的」花掉，别动永久积分

上游口径：**同一个号内部**先扣当日赠送、再扣永久积分（FEFO），但**跨号**它不管 ——
赠送额度按自然日清零、永久积分不过期，而赠送耗尽时上游不报错（静默改扣永久、照常 200）。
所以「先花今天会作废的」只能在选号侧做，本仓原本已有 `prefer_daily_quota`（余额 > 0 的
号进第 0 档）。上线后按 166 个号实测，发现三处会让流量漏到永久积分上的口子：

| 口子 | 后果 |
|---|---|
| 第 0 档只看 `dailyBalance > 0`，不看快照的周期日 | 跨日后旧快照仍写着余额，面板**主动**把流量送到「今天还没领到赠送」的号上 |
| 两次额度刷新（默认 30 分钟）之间余额是旧值 | 某个号当天赠送用尽后，面板还会继续用它 → 这段时间的消耗全计永久 |
| **会话粘性优先于分层**：绑定号健康就直接用，不看赠送 | 一条对话粘在赠送已尽的号上，之后每一轮都在烧永久（实测：只剩 5 分赠送的号被粘住后连烧 4 笔） |

另外每日赠送按自然日清零、新一天的额度要一次 first-login 才到账，而固定 30 分钟的
刷新 ticker 会把这一轮拖到 00:00–00:29 之间 —— 那之前池子里每个号都「今天还没有赠送」。

改法：

1. **本地当日记账** `Account.Charge(points)`：每次成功按上游口径把本地缓存的赠送余额
   扣掉（不够就归零，差额记进 `permBurned`），下一次额度刷新用上游真值覆盖，误差不累积。
   顺带修掉 `dailyConsumed` 从不清零的问题（原来它其实是「进程启动以来」）。
2. **第 0 档加周期日校验** `DailyUsableToday()`：余额 > 0 **且**快照周期日 = 今天。
   跨日/未知一律退到「只剩永久」档 —— 宁可少用一个号，也不烧永久。
3. **跨日那一刻立即刷一轮全池额度**（内含幂等 first-login，166 个号并发 4 约 40 秒），
   把「凌晨没有赠送」的空窗从最长 30 分钟压到几十秒。
4. **粘性给分层让位**：绑定号不在第 0 档、而池里还有号在第 0 档时，按「绑定不可用」
   处理 —— 走正常选号，成功后把绑定改写到新号（原本就会重绑）。池里没有更好选择时，
   粘性照旧生效，不会因此无号可用。
5. **当日记账落盘**（`dayKey` + 两个计数），否则重启后「今日」从零起算、名不副实。

面板「账号池」新增两格 KPI：**今日赠送剩余**（今天还会作废多少）与**今日永久消耗**
（应为 0，不为 0 就说明有请求落在赠送已尽的号上）—— 这是本次改动的验收指标。

### 为什么不按赠送余额排序

设第 i 个号当天赠送 d_i、实际消耗 u_i，则

```
永久消耗 = Σ max(0, u_i − d_i)
当日赠送浪费 = Σ d_i − Σ min(u_i, d_i) = Σ d_i − 总消耗 + 永久消耗
```

`Σ d_i` 与总消耗都由供需决定，所以**最小化浪费 ⟺ 最小化永久消耗**；而后者只要
「还有赠送余量的号没用完之前，绝不碰赠送已尽的号」就取到最优 —— 与余量在号之间
怎么分配无关。档内再按余额排序不但没有收益，还会打破余额/闲置/成功率的负载均衡。
（推论：若某天总需求 > 池内赠送总额，永久积分必然被消耗，与怎么选号无关，只能加号。）

验证（隔离实例 + 带状态的假上游，线上数据不参与）：

| 场景 | 结果 |
|---|---|
| acc-a 赠送只剩 5，一笔 20 分的请求 | 赠送归零、永久 +15，`今日永久消耗 = 15` |
| 加入 acc-b（赠送 5000）后再发 4 笔 | 4 笔**全部**落到 acc-b；acc-a 的永久消耗停在 15，acc-b 赠送 5000 → 4920 |
| 把 acc-b 的 `dailyCycleDate` 改成昨天 | `daily` 仍是 5000 但 `usable=false`，池汇总「今日赠送剩余」= 0（不会被当成今天还有赠送） |

线上基线（166 个号，2026-11-13）：池内今日消耗 44.8 万分，其中 `今日永久消耗 = 0`，
剩余赠送 59.9 万分与上游口径（830,000 − 230,923）逐分吻合。

新增用例：`TestChargeDrainsDailyLocally`、`TestDailyTierRejectsStaleSnapshot`、
`TestStickyYieldsToDailyTier`、`TestDailyCountersResetAcrossDay`、
`TestDailyAccountingSurvivesRestart`、`TestUntilNextDay`。
